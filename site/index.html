上下文在重复搬运，却看不出重复在哪

先用数据看清请求体的结构 —— 这决定了该优化什么。

1

输入是输出的 380 倍

实测 5000 次请求：输入 16.84 亿 tokens，输出仅 444 万。大头从来不是「模型想了多久」，而是「每次重发了多少历史」。

2

98.8% 的输入命中缓存

也就是说：这些内容本来就在被反复重发。优化方向不是少发请求，而是别把重复内容再传一遍。

3

却看不见重复在哪

客户端只告诉你发了多少，不告诉你请求体里什么在重复；换一个供应商，一切又从零开始猜。

4

协议与配置还得各配一遍

OpenAI / Anthropic / Responses 三种协议并存，每个客户端单独配 base_url 与密钥。

省下的 token 是实在的：不论上游怎么变，少发的 tokens 就不必再传输一遍。这也是为什么面板把省量按 token 逐项记账 —— 剥离 / 裁剪 / 缓存三类分开，看得见每一项省了多少。

核心能力

以省量为主线，其余三项都是为它服务。

主线

省量

剥离推理链、历史裁剪、响应缓存 —— 且不破坏上游 KV 缓存。

协议

协议自动匹配

客户端入口即意图；命中直传，字段不被往返翻译。

路由

模型别名与共存

中转 ID 与上游真名解耦；同名模型跨供应商各自成路由。

运维

可观测与韧性

省量逐项可见；熔断、退避重试、超时与体积上限。

协议由客户端决定，不由网关替你选

客户端打哪个入口，就用哪个协议转发 —— 上游本来就支持就直传，不支持才转换。

客户端入口网关行为发往上游
/v1/chat/completions命中即直传/chat/completions
/v1/messages命中即直传/messages
/v1/responses命中即直传/responses

为什么不让你手动勾

让配置者逐个模型勾选支持什么协议 —— 真实配置里 652 个模型无一勾选，功能等于不存在。

为什么也不靠猜

按模型名推断（claude-* → anthropic）会错：同名模型跨服务方协议不同，claude-opus-4-8 在官方走 anthropic、在转售商走 openai。

没证据时怎么办

没有任何证据说上游不支持 → 尊重客户端的选择。宁可让上游回一个诚实的错误，也不要静默换协议（后者会掩盖真实失败点）。

「直传」= 请求体逐字节保真：thinking 块与 signature、reasoning item 都不会被往返翻译掉。反之，转换必有代价 —— 这也是为什么 responses 直通路径的省量恒为 0（不经过剥离）。

剥离到什么程度，才不至于帮倒忙

剥离是有损且不可逆的 —— 所以边界要靠判据划，不能一刀切。

粗暴做法
把所有历史里的推理链都剥掉，省得最多
推理链与 tool_calls 常常是配对关系：要求二者并存时，剥了就得到 400 —— 省下的 token 还不够赔一次失败重试。
另一种做法
干脆不剥，保持请求体完全不变
最稳，但白白多付那部分推理链的传输费。实测这类内容在多轮会话里占比很高，且每轮都会重发。
我们的做法
分两层，且按上游协议判定（不是按供应商 —— 同一家常同时提供三种协议）：普通 assistant 推理链默认剥；带 tool_calls 的走协议开关；Anthropic 恒不剥
既拿到省量，又不制造必然失败的请求。anthropic_mode 那条优先于模型级开关 —— 宁可少省，也不能因为误勾而让请求必挂。
为什么按协议而非供应商
供应商只是换 endpoint，协议才决定剥离是否安全
实测反例：claude-opus-4-8 在官方走 anthropic、在转售商走 openai —— 按供应商开关必然误判。

剥不剥，先看协议，再看层

情形判定说明
Anthropic 协议绝不剥thinking 块必须连签名回传，剥了上游必回 400。这条优先于模型级开关 —— 宁可少省，也不能造出必然失败的请求。
chat 协议 · 普通 assistant剥默认开启。这是省量的基本盘。
chat 协议 · 带 tool_calls剥默认开启（实测安全）—— 这也是省量的大头（97.5%）。
Responses 协议 · reasoning item可选与相邻 function_call 的配对关系未经实测，剥掉可能因序列不合法而 400 —— 交用户在真实上游试开。
响应缓存 / 历史裁剪可选裁剪默认 0 = 关（优先保上下文）；缓存只对非流式生效。
三种协议、两层结构、一个总闸 —— 判定顺序不可颠倒：协议安全的红线优先于一切省量。三者也不叠加成「省得更多」就完事：剥离丢思考过程、裁剪丢历史、缓存只对非流式生效，所以默认只开代价最可控的那一项。

三步开始使用

为了部署简单，刻意把技术面做窄：单个可执行文件，无需 Node，也不需要静态文件目录。

1
拿到 exe从 爱发电 下载，或自行 cargo build --release（Rust 1.75+）
2
启动直接运行 AIGate.exe，首次启动自动生成 providers.json 与 .env；浏览器打开面板完成初始化
3
改客户端把编程工具的 API Base 指向 http://127.0.0.1:8787/v1，API Key 填任意值，模型 ID 用 providers.json 里的中转 ID

providers.json（路由与模型映射）

{
  "providers": [
    {
      "name": "deepseek",
      "endpoint": "https://api.deepseek.com/v1/chat/completions",
      "api_key_env": "DEEPSEEK_API_KEY",
      "models": {
        "deepseek-v4-flash-DS": {
          "upstream_model": "deepseek-v4-flash",
          "reasoning_effort": "max"
        }
      }
    }
  ]
}

.env（密钥与开关，部分热切换）

PORT=8787
DEEPSEEK_API_KEY=          # 变量名须与 api_key_env 一致
STRIP_HISTORY_REASONING=1  # 历史推理链瘦身
STRIP_TOOLCALL_ON_CHAT=1   # Chat 协议下剥离工具轮次
STRIP_TOOLCALL_ON_RESPONSES=0
MAX_HISTORY_TURNS=0        # 0 = 不裁剪
AIGATE_ADMIN_TOKEN=        # 留空则不鉴权

编辑 providers.json 后无需重启 —— 检测到文件变化会自动重载路由表。密钥只经环境变量注入，不写入代码或配置文件。

API 速查

三个入口协议，一个模型列表，一个健康检查。

方法路径说明
POST/v1/chat/completionsOpenAI 兼容，支持流式（SSE）与非流式
POST/v1/messagesAnthropic Claude 格式入口，自动双向转换；该协议下不剥离推理链
POST/v1/responsesOpenAI Responses 入口；上游同为 Responses 时原生直通，SSE 字节级透传
GET/v1/models返回可用模型列表，列表项即模型中转 ID
GET/health健康检查，返回 ok

路由采用精确匹配：客户端传的模型 ID 必须与 models 的 key 完全一致。不要在多个供应商下使用同一个中转 ID —— 路由表按 ID 索引，后配置者会静默覆盖前者。

常见问题

来自 README 的实战问答。

启动后闪退 / 无反应

检查 target/release/ 目录下是否有 providers.json 和 .env。首次启动会自动生成，如权限不足可手动创建空文件。更详细的错误信息会通过 Windows 消息框显示。

Token 统计为 0，或数字带 ≈ 前缀

带 ≈ 表示该条请求上游未返回 usage，AIGate 按可见文本估算（中文实际约 3 字节/token，估算偏保守），并标记为估算值而非实测。若大量请求都是估算，通常是上游不支持 usage 字段。

请求返回 404「未找到模型」

客户端传的模型 ID 不在 models 映射表中。检查 ID 是否完全匹配（含大小写、斜杠与供应商前缀）。可在面板「供应商」页或 GET /v1/models 查看可用 ID。

端口被占用

修改 .env 中的 PORT 变量，或设置系统环境变量 PORT。

如何新增一个供应商

① 在 providers.json 的 providers 数组中添加新条目；② 在 .env 中添加对应的 API Key 环境变量；③ 保存后自动生效（无需重启）。

项目

AIGate 是一个本地 LLM 网关：一个地址接入所有编程工具，一个面板管住所有模型供应商。本地运行、单文件交付。

数据口径：本页省量数字来自本机实测请求日志的审计结果，与面板「省量审计」同源。日志增长后数字会变化，请以你面板的实测为准。
