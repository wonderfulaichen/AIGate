推理链是「过程」，不是「结果」

客户端的做法是「把上一轮的全部回传」—— 但模型需要的从来是结果，不是自己上次怎么想的

✓必须回传
  • 用户的提问
  • 助手的最终回答
  • 工具调用的入参与返回
  • system 提示词
−可以剥掉
  • assistant 的 reasoning_content / reasoning
  • Responses 协议里独立的 reasoning item
  • reasoning_details（结构化思考）
推理链只在生成本轮回答的那一刻有用；回答已经产出，它的使命就结束了。把它回传给下一轮，既不改善回答质量，又让请求体随轮次线性增长 —— 这就是「重复搬运」的主体。

推理链越滚越大，而每轮都要重发

实测 10 轮会话：客户端发出的上下文一路增长，网关剥掉历史推理链后把它压平

不剥离11,510 B
剥离后3,210 B
末轮：客户端发出 11,513 B → 不剥离时上游收 11,510 B， 剥离后只收 3,210 B（省 8,300 B，72%）。
差值逐轮扩大（第 1 轮 −830 B → 第 10 轮 −8,300 B）：历史越长，重复搬运越多。

三种手段，各管一段

剥离是主力，另两项按需开启 —— 判据上一页讲过，这里只说各自省的是哪一块

剥离推理链

省的是「过程」：把历史里累积的推理链摘掉。这是省量的绝对主力 —— 实测占剥离总量的 97.5%。字段层面涉及 reasoning_content / reasoning / reasoning_details

历史裁剪

省的是「过早的轮次」：只保留最近 N 个 user 轮，更早的整段丢弃 —— 连带的工具链一起走，不会把一轮切一半。默认 0 = 不裁剪，因为丢历史会改变模型能看到的上下文

响应缓存

省的是「完全一样的请求」：非流式请求若字节级重复，直接本地回放，零 token 到上游。对同一条问题反复问的场景最有效

三者不叠加成「省得更多」就完事 —— 每一项都有明确的代价：剥离丢思考过程、裁剪丢历史、缓存只对非流式生效。所以默认只开代价最可控的那一项。

剥离到什么程度，才不至于帮倒忙

剥离是有损且不可逆的 —— 所以边界要靠判据划，不能一刀切

粗暴做法
把所有历史里的推理链都剥掉，省得最多
推理链与 tool_calls 常常是配对关系：客户端（或上游）要求二者并存时，剥了就得到 400 —— 省下的 token 还不够赔一次失败重试
另一种做法
干脆不剥，保持请求体完全不变
最稳，但白白多付那部分推理链的传输费。实测这类内容在多轮会话里占比很高，且每轮都会重发
我们的做法
分两层，且按上游协议判定（不是按供应商 —— 同一家常同时提供三种协议）：普通 assistant 推理链默认剥；带 tool_calls 的走协议开关；Anthropic 恒不剥
既拿到省量，又不制造必然失败的请求。anthropic_mode 那条优先于模型级开关 —— 宁可少省，也不能因为误勾而让请求必挂
为什么按协议而非供应商
供应商只是换 endpoint，协议才决定剥离是否安全
实测反例：claude-opus-4-8 在官方走 anthropic、在转售商走 openai —— 按供应商开关必然误判
代价与边界
剥离有损且不可逆
可选开启「降级可回取」：把被剔离的原文留档，事后可核查「这次到底删了什么」（默认关，因含思考明文）

AIGate.exe
后台服务管理面板路由与计量
  • 前端（HTML / CSS / JS）在编译期拼进可执行文件，不依赖 Node，也不需要静态文件目录
  • providers.json 描述供应商与模型；密钥走环境变量或面板管理，不落明文
  • 改端口或数据目录即可跑出互不干扰的多个实例
  • 上游调用是异步非阻塞的：单个慢上游不会拖住其他供应商的请求
