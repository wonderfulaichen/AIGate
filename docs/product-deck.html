「直传」意味着请求体逐字节保真：Anthropic 的 thinking 块与 signature、Responses 的 reasoning item 都不会被往返翻译掉。

原理：网关怎么知道上游支持什么

三路取证，按可靠性递减 —— 关键是零成本，不需要用户先点一次探测

1

端点路径信号

端点 URL 里带 /anthropic/ 或 /responses 段就直接读出来。注意只认有区分度的段：/chat/completions 是所有兼容网关的默认路径，不能当信号

2

内置目录

按服务方域名查表（不是按模型名）—— 同名模型跨服务方协议会不同，协议取决于谁在提供服务

3

HEAD 探测

对三个候选路径发 HEAD 请求：没有请求体 → 不触发生成 → 零 token。判据：404/501 = 不存在，其余（含 405 方法不允许）= 存在

4

对照哨兵

先探一个必定不存在的路径。若连它也返回「存在类」状态，说明该站对所有路径状态一致 —— 此时判定为不可判别并放弃，不给出假结论

三路结果取并集：客户端协议在集合内就直传；集合为空（= 没有任何「不支持」的证据）时尊重客户端选择，不静默改协议。

省量：三种手段，各自的判据

叠加使用，但取舍都有明确理由 —— 不是能省就省

剥离推理链

剥掉带 tool_calls 的 assistant 消息里的推理链。Anthropic 链路一律不剥：extended thinking 的 thinking 块必须连签名原样回传，剥掉会 400。开关粒度按模型而非供应商 —— 同一中转下混着多种协议

历史裁剪

只保留最近 N 个 user 轮。默认 0 = 不裁剪，优先保上下文完整性；真超限时由紧急瘦身兜底

响应缓存

只缓存 stream:false 且 2xx 的响应。键 = 去掉 stream 字段后的请求体做确定性序列化，内存受条目上限 + TTL 双约束

被剥离的内容绝大多数落在上游的缓存命中区，而命中价与未命中价相差数十倍 —— 所以省下的金额远小于 token 数给人的印象。决定成本的始终是上下文规模本身。

原理：剥离为什么不破坏缓存，以及超限怎么办

两个容易被忽略的点 —— 也是「省量到底有没有用」的关键

1

剥离位置的选择

只剥「带 tool_calls 的 assistant 消息」里的推理链，不动其余部分。这样改动集中在追加区之后，前面已有的前缀不受影响

2

与 KV 前缀缓存的关系

上游的前缀缓存按前缀命中。剥离改变的是靠后的内容，故不破坏已缓存的前缀 —— 命中率仍然很高，省下的是那部分本该按命中价计费的重复上下文

3

紧急瘦身兜底

请求体超过供应商上限（如某些网关约 1MB）时，网关在转发前递进裁剪历史，目标压到上限的 90%，避免白白打到上游被裸拒

4

tool 输出常态截断

与紧急瘦身不同：这是不等超限就做的常态截断 —— 单条工具输出过长时按配置上限截断，防止一次读取把上下文顶满

所有省量动作都会单独记账（剥离省了多少、裁剪省了多少、缓存省了多少），面板上可逐项核对，不是一笔糊涂账。

原理：坏上游怎么被隔离，又怎么自动恢复

按供应商维度做熔断 —— 状态机三态，参数写在配置里

1

Closed（正常）

正常放行。同时维护一个长度为 20 的近期窗口，记录成功与失败

2

Open（熔断）

触发条件二选一：连续失败达 4 次，或窗口内错误率超过 60%。此后对该供应商快速失败，不再把请求打向已挂的端点

3

HalfOpen（探测）

熔断后等 60 秒，放行单个探测请求。其余请求仍被拒绝，避免探测期被流量压垮

4

恢复

探测连续成功 2 次即回到 Closed；失败则重新计时等下一轮

设计要点：探测名额只允许被同一个请求认领一次。若实现里被同一请求消耗两次，探测就永远发不出去、熔断永不自动恢复 —— 这类缺陷不报错，只表现为「一直 503，只能手动重置」。

原理：费用是怎么算出来的

价格不是一个数，而是按「三种 token × 高峰/空闲」组合出来的

1

三种 token 分别计价

输入、输出、缓存命中各有一个单价。缓存命中价通常是输入价的零头 —— 所以「命中率」直接决定账单

2

高峰与空闲两套价

支持分时段计费：同一模型可配高峰价与空闲价两套，按请求时刻落在哪个时段取价

3

缺失字段的回落

没配缓存价 → 回退按输入价计；没配空闲价 → 回退高峰价。确保任何模型都能算出数，不会因为缺一项就显示不出来

4

上游没给 usage 时

按响应体字节数 ÷ 4 估算 token，并在日志里标记usage_estimated —— 面板据此区分「实测」与「估算」，不混为一谈

费用只是「估算」而非账单：面板上会明确写出这一点，且当窗口内请求的模型都没配价时显示为「—」而不是 0 —— 「没配价」与「免费」是两件事。

原理：怎么发现模型开始「鬼打墙」

推理模型偶发陷入重复输出，会一直烧 token 直到上限 —— 需要在流式过程中就识别出来

1

检测方式

边收流边在滑动窗口内查找：是否存在某个长度为 L 的子串连续重复达到设定次数

2

按字符而非字节

窗口切片以字符为单位。上游流里含中文时，按字节偏移切窗口极易切在字符中间，导致误判或漏判

3

触发后的动作

判定为死循环即中断该次转发并如实报错，同时记入日志 —— 避免继续按输出 token 计费

4

可按模型关闭

个别模型正常输出也会高频重复（如格式化生成），可对该模型单独关闭守卫

这是「省钱」与「正确性」的交汇点：一次失控的输出可能比正常请求贵几十倍。

界面：暗色与亮色，同一套设计语言

首帧即正确，不会先闪一下暗色；主题在顶栏随时切换

看得见每一次请求

花了多少、慢在哪、为什么失败 —— 都在面板里，不用翻日志文件

供应商与模型，一处管住

卡片与表格双视图；拉取模型时自动探测上游支持的协议

一个二进制，扔到机器上就能跑

为了部署简单，刻意把技术面做窄

AIGate.exe
后台服务管理面板路由与计量
  • 前端（HTML / CSS / JS）在编译期拼进可执行文件，不依赖 Node，也不需要静态文件目录
  • providers.json 描述供应商与模型；密钥走环境变量或面板管理，不落明文
  • 改端口或数据目录即可跑出互不干扰的多个实例
  • 上游调用是异步非阻塞的：单个慢上游不会拖住其他供应商的请求

Rust · axum · 单进程异步

三步开始使用

1
拿到 exe从发行版下载，或自行 cargo build --release
2
启动直接运行 AIGate.exe，浏览器打开面板完成初始化
3
改客户端把编程工具的 API Base 指向 http://127.0.0.1:8787/v1
